# 传送点设计

## 官方名字

游戏里叫 **「协议传送点」**（`I18nTextTable_CN` 里能查到，配套文案是
「在协议传送点休整后，全队干员防御力增加」「可前往附近协议传送点取至背包」）。

⇒ **它就是营地机制**：地图标记模板 `mark_sp_campfire`，互动物 `int_campfire_v2`。

## 能拿到坐标的地方

### 1. `MapMarkInsTable`（便宜，但只覆盖 map01）

带 `levelId` + `pos`(Vector3) + `logicId`，是**手工摆放的静态标记**：营地、工厂解锁点、箭头。
每个 map01 区域 2~7 个，密度正合「一个区域里有好几个传送点」。

**但 map02 只有 3 行，而且没有一个落在自己区域的矩形内**（坐标帧对不上）。
⇒ 只能服务 map01，**不是通用真源**。

相关类型：`Beyond.Cfg.MapMarkInsData`（`markInsId` / `levelId` / `markInfoId` / `pos` /
`logicId` / `activeMethod`）、`MapMarkTypeData`（`category` / `markInfoType` / `name` / `icon`）。
`MarkInfoType` 枚举里有 TravelPole（滑索）、Campfire、Dungeon、HUB 等。

### 2. `LevelData.interactives`（通用真源，成本高）

MemoryPack 侧的关卡实体数据，`LevelInteractiveData` 继承 `LevelEntityData`，后者带
`entityDataIdKey` / `entityType` / `levelLogicId` / `position` / `rotation` / `scale`。
`levelLogicId` 与 `MapMarkInsData.logicId` 同域，两边能对上。

细节与解码进度见 [关卡逻辑数据.md](关卡逻辑数据.md)。

## 传送点类互动物的 id

来自 `Data/Json/Interactive/InteractiveData/` 的文件名（明文即 id）：

`int_campfire_v2`、`int_loading_portal`、`int_seamless_portal`、`int_simple_travel_pole`、
`int_fac_travel_pole_1/2`、`int_system_dungeon_entry`、`int_race_teleporter`。

## 已排除的地方（别再查）

| 查过 | 结论 |
|---|---|
| `MapMarkTypeTable` / `DomainPoiTable` | 只有类型目录（图标 + 名字），**无坐标** |
| `UILevelMapLoadConfig.staticElements` | 是地图 UI 装饰：区域文字 / 雾 / 切换按钮（见 `UILevelMapStaticElementType`） |
| `arts/gameplay/interactive` 下的摆放 | 全是**可破坏树木**，不是传送点 |
| `FBDynamicScenePoiControlComp` | schema 里有（`EDynamicSystem.PoiControl = 43`），**发布数据里全为空**。组件图的遍历链 root → `comps` → `data_index` → 按 `EDynamicSystem` 分派 已写对并验证过，是数据不在那儿 |
| `InteractiveMarkDataTable` | 只有 10 行建筑类，无坐标 |
